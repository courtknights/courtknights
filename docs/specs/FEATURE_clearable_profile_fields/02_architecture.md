## Overview

`PUT /api/v1/users/me/profile` becomes `PATCH /api/v1/users/me/profile` with
JSON Merge Patch (RFC 7396) semantics. The change runs through the existing
FEATURE_user_profile layers (ADR-008) without new packages:

- **Handler** — decodes the body member by member, so it can tell an omitted
  member from an explicit `null`, and validates values (types, enums, empty
  strings, `display_name: null`).
- **Domain** — a tri-state `Field[T]` (unchanged / cleared / set) replaces the
  `*T` fields of `ProfilePatch`, which could only express "unchanged" or "set".
- **Manager** — applies the location rules, which need the stored profile
  (country change clears the region; a region alone is checked against the
  stored country).
- **Repository** — writes `NULL` for cleared columns and merges `preferences`
  inside PostgreSQL with `jsonb` operators, so a partial preferences update
  never overwrites keys it does not mention.

A `CHECK` constraint keeps `region` consistent with `country` even under
concurrent writes. Read endpoints are unchanged.

## Domain model changes

### `Field[T]` — tri-state patch value

```go
// api/internal/domain/profile/patch.go

// Field is one member of a JSON Merge Patch (RFC 7396).
//   - zero value (Set == false): the member was omitted → leave unchanged
//   - Set == true, Value == nil: the member was null    → clear
//   - Set == true, Value != nil: the member had a value → set
type Field[T any] struct {
    Set   bool
    Value *T
}

func Unchanged[T any]() Field[T]  // Field[T]{}
func Cleared[T any]() Field[T]    // Field[T]{Set: true}
func SetTo[T any](v T) Field[T]   // Field[T]{Set: true, Value: &v}

// IsClear reports whether the field clears the stored value.
func (f Field[T]) IsClear() bool
```

### `ProfilePatch` (replaces the current `*T`-based struct)

```go
// ProfilePatch is a JSON Merge Patch of a Profile.
type ProfilePatch struct {
    // DisplayName is mandatory: it can be changed but never cleared, so it
    // stays a plain pointer (nil = unchanged).
    DisplayName *string
    City        Field[string]
    Region      Field[string]
    Country     Field[string]
    Gender      Field[Gender]
    DateOfBirth Field[time.Time]
    Category    Field[Category]
    Preferences PreferencesPatch
}

// PreferencesPatch merges into the stored preferences (RFC 7396, recursive).
type PreferencesPatch struct {
    // Clear is true for "preferences": null — every preference is removed
    // before the members below are applied.
    Clear      bool
    CourtSide  Field[CourtSide]
    Handedness Field[Handedness]
}

// IsEmpty reports whether the patch changes nothing.
func (p ProfilePatch) IsEmpty() bool
```

`Preferences`, `Profile` and the enums are unchanged. Adding a future
preference means adding one `Field` to `PreferencesPatch` plus its JSON key.

### New sentinel error

```go
// api/internal/domain/ckerrors/profile.go

// ErrProfileConflict is returned when a profile write violates a consistency
// constraint because of a concurrent update (region/country check).
ErrProfileConflict = errors.New("profile changed concurrently")
```

## API design

### `PATCH /api/v1/users/me/profile`

```
PATCH /api/v1/users/me/profile
Authorization: Bearer <jwt>
Content-Type: application/merge-patch+json   (application/json is also accepted)
```

**Request** — any subset of the members below:

```json
{
  "display_name": "Álvaro",
  "city": null,
  "region": "ES-MD",
  "country": "ES",
  "gender": null,
  "date_of_birth": "1990-05-14",
  "category": "third",
  "preferences": { "court_side": "drive", "handedness": null }
}
```

| Member | Value | `null` |
|--------|-------|--------|
| `display_name` | non-blank string | `400` (mandatory field) |
| `city` | non-blank string | clears |
| `country` | ISO 3166-1 alpha-2, uppercase | clears (and the region, see below) |
| `region` | ISO 3166-2 code of the effective country | clears |
| `gender` | `male` \| `female` | clears |
| `date_of_birth` | `YYYY-MM-DD` | clears |
| `category` | `first` … `fifth` | clears |
| `preferences` | object, merged recursively | clears all preferences (`{}`) |
| `preferences.court_side` | `drive` \| `backhand` \| `both` | removes the key |
| `preferences.handedness` | `right` \| `left` | removes the key |

**Response `200`** — the updated profile, same shape as `GET /users/me/profile`
(cleared fields serialise as `null`; cleared preferences are absent from the
`preferences` object).

**Errors**

| Status | When |
|--------|------|
| `400` | Body is not a JSON object; a member has the wrong JSON type; an enum or date is invalid; a string is empty or whitespace-only; `display_name` is `null`; `preferences` is not an object or `null`; an unknown member (top level or inside `preferences`); an invalid location (see *Location rules*) |
| `404` | The caller has no profile (`ErrProfileNotFound`) |
| `409` | The region/country consistency check failed because of a concurrent update (`ErrProfileConflict`); the client retries |
| `415` | `Content-Type` is neither `application/merge-patch+json` nor `application/json` |
| `500` | Any other failure; generic message, never the internal error text |

An empty object `{}` is valid and returns the current profile unchanged.

### `PUT /api/v1/users/me/profile` — removed

The route is deleted and the request returns `404 Not Found`. The protected
`/api/v1` group has middleware (JWT), and Echo then registers catch-all routes
that answer 404 for any unregistered method on the group, so every endpoint of
the API behaves this way (decided by the architect during TASK-005).

### Location rules (applied by the manager)

Let *stored* be the current profile and *effective country* the country after
the patch (`patch.Country` if present, otherwise the stored country).

1. `country` present with a value → must be a valid ISO 3166-1 alpha-2 code.
2. `country` present and **different** from the stored country (changed or
   cleared), and `region` **absent** → the region is cleared.
   `country` present with the **same** value as stored → the region is kept.
3. `region` present with a value → the effective country must be set and the
   region must belong to it. `region` alone is therefore checked against the
   stored country (supersedes FEATURE_user_profile AC-05 "region without
   country → 400").
4. `country: null` and `region: "<code>"` in the same request → `400` (no
   effective country).

| Stored | Patch | Result |
|--------|-------|--------|
| `ES` / `ES-MD` | `{"country": "FR"}` | `FR` / `null` |
| `ES` / `ES-MD` | `{"country": "FR", "region": "FR-IDF"}` | `FR` / `FR-IDF` |
| `ES` / `ES-MD` | `{"country": "ES"}` | `ES` / `ES-MD` |
| `ES` / `ES-MD` | `{"country": null}` | `null` / `null` |
| `ES` / `ES-MD` | `{"region": "ES-CT"}` | `ES` / `ES-CT` |
| `ES` / — | `{"region": "FR-IDF"}` | `400` |
| — / — | `{"region": "ES-MD"}` | `400` |
| `ES` / `ES-MD` | `{"region": null}` | `ES` / `null` |

## Database changes

Migration `005_user_profiles_region_country_check`:

```sql
-- up
ALTER TABLE user_profiles
    ADD CONSTRAINT user_profiles_region_country_check
    CHECK (region IS NULL OR (country IS NOT NULL AND region LIKE country || '-%'));

-- down
ALTER TABLE user_profiles DROP CONSTRAINT IF EXISTS user_profiles_region_country_check;
```

ISO 3166-2 codes start with the alpha-2 country code and a hyphen, so the
check rejects a region without a country or from another country. Full code
validity stays in the domain (`ValidateLocation`). Existing rows already
satisfy it: every write so far went through `ValidateLocation`, which enforced
both rules. The up migration fails loudly if a row does not.

The check only matters for a race: the manager validates against the profile
it read, and a concurrent request can change the country before the write.
The repository maps the violation (`23514`, constraint
`user_profiles_region_country_check`) to `ckerrors.ErrProfileConflict` → `409`.

`db/schema/user_profiles.sql` gains the constraint.

### Repository `Update` SQL

Each `Field` that is `Set` adds `col = $n`, binding the value or `NULL`.
Preferences are merged in one expression, emitted only when the preferences
patch changes something:

```sql
preferences = (
    (CASE WHEN $clear THEN '{}'::jsonb ELSE preferences END)  -- "preferences": null
    || $set::jsonb                                             -- members with a value
) - $remove::text[]                                            -- members that are null
```

For `{"preferences": {"court_side": "drive", "handedness": null}}`:
`$clear = false`, `$set = {"court_side":"drive"}`, `$remove = {handedness}`.
The merge happens in the `UPDATE`, so it never loses a preference written by a
concurrent request. `updated_at` is set on every non-empty patch; an empty
patch returns the current profile without writing.

## Internal package structure

```
api/internal/
  domain/
    profile/
      patch.go            # NEW — Field[T], ProfilePatch, PreferencesPatch (moved from repository.go)
      repository.go       # Update(ctx, userID, ProfilePatch) — same signature, new type
    ckerrors/
      profile.go          # + ErrProfileConflict
  application/
    profile/
      manager.go          # Update: loads the stored profile, applies location rules
  infrastructure/
    postgres/
      profile_repository.go  # Update: NULL for cleared fields, jsonb merge, 23514 → ErrProfileConflict
  api/
    common/
      mergepatch.go       # NEW — DecodeMergePatch: content type + JSON object → map[string]json.RawMessage
    profile/
      handler.go          # updateMyProfile parses the merge patch; PUT handler removed
      routes.go           # PATCH /users/me/profile (PUT removed)
db/
  migrations/005_user_profiles_region_country_check.{up,down}.sql   # NEW
  schema/user_profiles.sql                                          # + CHECK
docs/
  decisions/ADR-015_partial-updates-json-merge-patch.md             # NEW (TASK-001)
```

`common.DecodeMergePatch` is generic (no profile knowledge) so later partial
update endpoints follow the same rules (ADR-015). It:

1. Accepts `application/merge-patch+json` or `application/json` (parameters
   such as `charset` ignored), otherwise returns a `415` error.
2. Decodes the body into `map[string]json.RawMessage`; anything other than a
   JSON object is a `400`.

Member-level parsing (types, enums, `null` handling) stays in the profile
handler, which owns HTTP validation (ADR-008).

## New architectural decisions

**ADR-015 — Partial updates use JSON Merge Patch (RFC 7396).** Recorded in
[ADR-015](../../decisions/ADR-015_partial-updates-json-merge-patch.md)
(TASK-001). Summary:

- Partial updates use `PATCH` with RFC 7396 semantics: omitted → unchanged,
  `null` → cleared, value → set, nested objects merged recursively.
- Both `application/merge-patch+json` and `application/json` are accepted;
  other media types → `415`.
- `null` on a mandatory field → `400`. Empty or whitespace-only strings →
  `400`; `null` is the only way to clear.
- Unknown members → `400`, so a typo is never silently ignored.
- `PUT` is reserved for full replacement and is not used for partial updates.

## Rollout and compatibility

- `PUT /users/me/profile` disappears: any external script must switch to
  `PATCH`. No client in the repo uses it (`web/` and `e2e/` have no calls).
- `null` in a `PUT` body used to mean "unchanged"; in `PATCH` it clears. A
  client that blindly forwards a full object with `null`s would now clear those
  fields — documented in ADR-015 and the PR.
- Migration 005 must run before the new code is deployed (the repository maps
  the constraint violation; older code works with or without it).

## Resolved decisions

Answered by the human architect on 2026-10-12:

1. **Unknown members → `400`.** Top-level and `preferences` members that the
   API does not know are rejected, so a typo such as `"date_of_brith"` is
   never silently ignored.
2. **`CHECK` constraint + `409`.** Migration 005 and `ErrProfileConflict` are
   kept (TASK-002) as defense in depth against the read-validate-write race.
3. **ADR-015 is a global convention.** Every future partial-update endpoint
   uses `PATCH` with RFC 7396 and the same rules (TASK-001).
4. **Same country keeps the region.** `{"country": "ES"}` on `ES` / `ES-MD`
   leaves `ES-MD`; the region is cleared only when the country actually
   changes or is cleared (rule 2 of *Location rules*).
