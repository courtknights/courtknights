## Overview

This feature reorganises the CourtKnights monorepo from a flat root structure into five
explicit workspaces (`api/`, `web/`, `db/`, `infra/`, `e2e/`), each owning its toolchain,
dependency manifest, and local `Makefile`. The Go source tree (`cmd/`, `internal/`) moves
into `api/` with its own `go.mod`; database schema and migrations move into a top-level
`db/` workspace. A `go.work` file at the repository root coordinates the Go workspace.
The root `Makefile` becomes a thin dispatcher that delegates to each workspace `Makefile`.
`infra/` and `e2e/` are scaffolded with a README and a placeholder config. No application
logic, APIs, or database schema are modified.

## Go workspace configuration

### `go.work` (repository root)

```
go 1.25

use ./api
```

The `go.work` file is **committed** to the repository. All `go` commands run from the
repository root resolve modules through `go.work`. This allows tooling (editors, CI) to
operate from the root without needing to `cd api/` first.

### Module path

The module path in `api/go.mod` stays **unchanged**:

```
module github.com/courtknights/courtknights
```

All existing internal import paths (e.g. `github.com/courtknights/courtknights/internal/…`)
remain valid with no edits required to Go source files.

### `.gitignore` additions

`api/build/` must be added to `.gitignore` (or the existing `build/` entry updated to
`api/build/`).

## Makefile strategy

### Root `Makefile`

The root `Makefile` delegates every workspace-specific target via `$(MAKE) -C <workspace>`:

```makefile
# Root Makefile — dispatcher

.PHONY: build run test test-int test-all lint fmt clean \
        db-migrate db-rollback db-status \
        web-install web-start web-build web-test

## api targets
build:
	$(MAKE) -C api build

run:
	$(MAKE) -C api run

test:
	$(MAKE) -C api test

test-int:
	$(MAKE) -C api test-int

test-all:
	$(MAKE) -C api test-all

lint:
	$(MAKE) -C api lint

fmt:
	$(MAKE) -C api fmt

clean:
	$(MAKE) -C api clean

## db targets
db-migrate:
	$(MAKE) -C db migrate

db-rollback:
	$(MAKE) -C db rollback

db-status:
	$(MAKE) -C db status

## web targets
web-install:
	$(MAKE) -C web install

web-start:
	$(MAKE) -C web start

web-build:
	$(MAKE) -C web build

web-test:
	$(MAKE) -C web test
```

### `api/Makefile`

The existing root `Makefile` content moves verbatim into `api/Makefile`, with path
adjustments:

- `CMD_SERVER := ./cmd/server` — unchanged (relative to `api/`)
- `BUILD_DIR := build` — resolves to `api/build/`
- All `go` commands run within `api/` context (no `go.work` redirection needed when
  invoked via `$(MAKE) -C api`)

### `web/Makefile`

A minimal `web/Makefile` is added to expose the standard npm scripts as Make targets,
so the root dispatcher can call them uniformly:

```makefile
.PHONY: install start build test

install:
	npm install

start:
	npm start

build:
	npm run build

test:
	npm test
```

## `db/` workspace

`db/` is a first-class workspace — not nested inside `api/`. It has no `go.mod` because
it owns SQL files, not Go code. The Go application reads migration files at deploy time
via a path configured in `docker-compose.dev.yml` and any future deployment tooling.

### `db/Makefile`

The migration tool is **`golang-migrate`** (see ADR-010 below). The CLI binary
(`migrate`) must be available in the development environment and in CI.

```makefile
.PHONY: migrate rollback status

DB_URL ?= postgres://postgres:postgres@localhost:5432/courtknights?sslmode=disable
MIGRATIONS_DIR := ./migrations

## migrate: apply all pending migrations
migrate:
	migrate -path $(MIGRATIONS_DIR) -database "$(DB_URL)" up

## rollback: revert the last applied migration
rollback:
	migrate -path $(MIGRATIONS_DIR) -database "$(DB_URL)" down 1

## status: show current migration version
status:
	migrate -path $(MIGRATIONS_DIR) -database "$(DB_URL)" version
```

`DB_URL` is overridable via environment variable so CI and local environments can pass
their own connection strings without modifying the Makefile.

## New architectural decisions

### ADR-010 — Database migration tool: `golang-migrate`

**Decision:** Use [`golang-migrate`](https://github.com/golang-migrate/migrate) as the
database migration tool. Migrations are plain SQL files (`.up.sql` / `.down.sql`) stored
in `db/migrations/`. The `migrate` CLI is used directly from `db/Makefile`.

**Rationale:**
- SQL-first: migrations are plain `.sql` files, not Go code — readable by anyone
  regardless of Go knowledge, and executable without compiling the application.
- Widely adopted, actively maintained, supports PostgreSQL natively.
- CLI + Go library: can be invoked from the Makefile for development and embedded in the
  application binary for automated startup migrations if needed in the future.
- No DSL to learn — standard `UP` / `DOWN` SQL pairs.

**Consequences:**
- The `migrate` CLI binary must be installed in developer environments and in CI.
- Migration file naming follows the `golang-migrate` convention:
  `{version}_{description}.up.sql` / `{version}_{description}.down.sql`
  (e.g. `000001_create_users.up.sql`).
- `DB_URL` must be available as an environment variable in all contexts that run
  migrations.

> This decision must be formalised as `docs/decisions/ADR-010_migration-tool-golang-migrate.md`
> before implementation begins.

---

### ADR-009 — Go workspace with `go.work`

**Decision:** A `go.work` file at the repository root coordinates the `api/` Go module.
The file is committed.

**Rationale:**
- Allows `go` tooling and editors to operate from the repository root without requiring
  `cd api/`.
- Native Go feature (stable since Go 1.18, fully supported in Go 1.22+). No third-party
  tooling required.
- Keeps the monorepo extensible: future Go modules (e.g. a CLI tool) can be added as
  additional `use` entries.

**Consequences:**
- `go.work.sum` is generated automatically and must be committed alongside `go.work`.
- Developers must run `go work sync` after adding a new Go module to the workspace.

> This decision must be formalised as `docs/decisions/ADR-009_go-workspace.md` before
> implementation begins.
